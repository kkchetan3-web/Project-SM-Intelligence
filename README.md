# Satta Matka Quantitative Research Platform

A reproducible research platform for testing — rigorously, and with the null hypothesis
given every chance to win — whether the digit outcomes published by Satta Matka markets
contain any structure that could be forecast.

It implements **100 documented mathematical methods**, a **per-market SQLite data layer**
with full provenance and revision history, a **leakage-audited cross-market engine**, and a
**strict walk-forward backtester** that compares every candidate model against seven naive
baselines under a pre-committed promotion rule.

> ## Read this before anything else
>
> **1. No real market data was obtained.** All five configured sources were unreachable from
> the environment this platform was built in (TLS resets on port 443, empty replies on port 80).
> Every number in this repository is computed on **synthetic control data** that is labelled
> `verification_status='synthetic_control'` in the database and cannot be reported as live
> history. This is not a limitation of the analysis — it is the honest state of the extraction
> pipeline: it has never seen a real page.
>
> **2. No predictive edge was found.** Under the stated promotion rule, no candidate model beat
> the best naive baseline out of sample, on any market, target or dataset. The platform forecasts
> from baselines and labels every such forecast as carrying no demonstrated information.
>
> **3. This is not gambling advice.** Nothing here should be used to stake money. Historical
> frequencies do not become future probabilities, "hot" and "cold" numbers carry no obligation
> to reverse, and chasing losses is never rational.

## Why the data is synthetic, and why that is still worth something

The platform ships two **control worlds** with known ground truth. They are the only honest way
to test a forecasting framework whose real data source is unavailable:

| World | Data-generating process | Correct answer | Purpose |
|---|---|---|---|
| `synthetic_null` | Independent uniform draws (H0) | **No edge exists** | Proves the framework stays silent on noise |
| `synthetic_signal` | Planted first-order persistence + a Kalyan→Main Bazar channel (H1) | **Edge exists** | Proves the framework can detect structure when it is there |

3,131 draws per market, Mon–Sat, 2016-01-01 → 2025-12-31, identical calendar in both worlds so
that only the dependence structure differs. Parameters are recorded in each row's `raw_payload`.

A framework that "finds" structure in the null world is broken. A framework that finds nothing
in the signal world is too weak to be trusted. Both directions are tested in CI and in
`docs/RESULTS_*.md`.

## Measured results: the framework against both controls

These are the numbers the platform produced on its two control worlds. They are
regenerated by `python scripts/summarise_results.py --dataset <name> --write` into
[`docs/RESULTS_synthetic_null.md`](docs/RESULTS_synthetic_null.md) and
[`docs/RESULTS_synthetic_signal.md`](docs/RESULTS_synthetic_signal.md), read straight
from the databases.

| Quantity | `synthetic_null` (H0: nothing to find) | `synthetic_signal` (H1: structure planted) |
|---|---|---|
| Findings surviving BH-FDR at 0.05 (K/O, K/C, M/O, M/C) | **0 / 0 / 0 / 0** | **34 / 35 / 34 / 37** |
| Best baseline log loss (uniform floor = 2.30259) | `uniform` 2.30259 | `markov1` 2.0813 – 2.2477 |
| Best candidate model log loss | `svm` 2.3078 – 2.3088 (worse than uniform) | `catboost` 2.1190 – 2.2431 |
| Models promoted by the rule | **none** | **none** |
| Cross-market lag tests significant after Holm | **0 of 28** | **3 of 28** |
| Conditional-model tests with a demonstrated improvement | **0 of 4** | **1 of 4** (Main Bazar Close, +0.02803 LL, CI excludes zero) |
| Forecast issued | uniform, labelled `baseline_fallback` | `markov1`, labelled `baseline_fallback` |

What that contrast means:

- **On the null world the framework is silent.** Not "quiet" — silent: zero FDR
  survivors, zero cross-market hits, and every one of the ten estimators is *worse*
  than the uniform floor, which is what a model can only do when there is no signal.
- **On the signal world it fires, and in the right places.** The surviving findings
  are the ones that should survive first-order Markov dependence: goodness-of-fit
  (M009), transition chi-square with Cramér's V ≈ 0.22–0.28 (M023), mutual
  information (M031), runs and parity tests (M053/M061). Second-order tests correctly
  find nothing extra, because the generator is first-order.
- **It still refuses to claim predictability.** The best baseline (`markov1`) beats
  every learned model on the signal world, and the one model that did edge past it —
  Main Bazar Close, `catboost`, by 0.0046 log loss — was rejected by the promotion
  rule: its bootstrap CI `[-0.0193, +0.0115]` includes zero and its calibration slope
  is 0.725, outside `[0.80, 1.25]`. So no forecast anywhere in this repository is
  presented as informed, on either world.

That is the honest summary of the whole project: **the machinery works, the data has
no exploitable edge, and the platform says so.**

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt && pip install -e . --no-deps

# 1. Build the control world and its per-market databases
python -m src.cli.main --dataset synthetic_null init
python -m src.cli.main --dataset synthetic_null synthetic

# 2. Validate, then run all 100 methods for every market and target
python -m src.cli.main --dataset synthetic_null validate
python -m src.cli.main --dataset synthetic_null analyse        # ~4 min per market/target

# 3. Backtest, cross-market, forecast, report
python -m src.cli.main --dataset synthetic_null backtest --market kalyan
python -m src.cli.main --dataset synthetic_null cross-market
python -m src.cli.main --dataset synthetic_null predict --market kalyan --target open
python -m src.cli.main --dataset synthetic_null report

# Or run the whole chain and write a machine-generated result summary
python scripts/run_full_pipeline.py --dataset synthetic_null
python scripts/summarise_results.py --dataset synthetic_null --write
```

`make help` lists the same operations as targets.

### One database per market

`data/databases/<market_id>/<market_id>.db`, each with the twelve required tables
(`historical_results`, `source_records`, `extraction_runs`, `data_quality`, `market_features`,
`method_results`, `model_registry`, `backtest_results`, `predictions`, `prediction_outcomes`,
`cross_market_features`, `cross_market_tests`) plus `result_revisions`, `update_history`,
`database_identity` and `database_migrations`.

Nothing merges Kalyan into Main Bazar. A cross-market test is written into **both** markets'
databases because it is a fact about both, but every model, feature matrix, backtest and
forecast belongs to exactly one market.

**The raw layer is never rewritten.** A corrected result inserts a `result_revisions` row holding
the old value, the new value, the source and the timestamp; the live row is updated and the
audit trail is append-only. Impossible values (an ank outside 0–9, a non-3-digit panna) are
rejected by CHECK constraints before any quality check sees them.

## The 100 methods

| Category | Range | Focus |
|---|---|---|
| A | M001–M012 | Frequency and marginal distribution |
| B | M013–M022 | Recurrence, gaps and "due number" hypotheses |
| C | M023–M034 | Markov chains and transition structure |
| D | M035–M046 | Time-series and temporal structure |
| E | M047–M060 | Number theory and digit arithmetic |
| F | M061–M072 | Randomness, entropy and uniformity testing |
| G | M073–M084 | Machine learning |
| H | M085–M100 | Advanced statistics and meta-analysis |

Each method produces one of five honest statuses — `computed`, `not_applicable`,
`insufficient_data`, `dependency_unavailable`, `failed` — and every computed number carries the
sample size that produced it. There is no code path that emits a metric without a sample size or
a fabricated placeholder.

`python -m src.cli.main methods --write --market kalyan` renders a fifteen-section dossier per
method into `research/methods/`: definition and mathematical foundation, objective, formula,
variable definitions, assumptions, input requirements, manual steps, a **clearly-labelled
hypothetical** worked example, the **actual** computed results from the database, separate Open
and Close findings, suitability, stability, interpretation, limitations and conclusion.

## Leakage policy

Three rules, enforced in code and tested:

1. **Walk-forward only.** Every prediction comes from a model fitted on data strictly before the
   target date. `verify_causality` rebuilds the feature matrix on truncated history and asserts
   the prefix is unchanged; `--strict-markers` tests tamper with future values and assert that
   earlier predictions do not move.
2. **A foreign market's same-day value is inadmissible by default.** Publication timestamps
   cannot be verified from historical chart pages, so the engine uses lag ≥ 1 for cross-market
   features. The single exception is declared explicitly in `config/markets.yaml`:
   ```yaml
   cross_open_precedence:
     - ["kalyan", "main_bazar"]   # Kalyan's Open is published before Main Bazar's Close
   ```
   That declaration is an **assumption**, stated as one, and every feature frame records whether
   the channel was used (`causality["same_day_foreign_open_used"]`). Delete the entry and the
   channel disappears — there is a test for that.
3. **No re-use of the evaluation window.** Multiple-testing control (Benjamini–Hochberg) is
   applied across the whole 100-method sweep before any finding is called significant.

## Promotion rule

A candidate model is only ever used for forecasting if **all** of the following hold on the
out-of-sample walk-forward window:

- it beats the **best** naive baseline by at least **0.002** log loss;
- the paired moving-block bootstrap 95% CI of the difference excludes zero;
- it wins in more than half of the chronological folds;
- its calibration slope lies in **[0.80, 1.25]**.

Otherwise `promoted = False`, and the prediction engine falls back to the best baseline,
labelling the output `baseline_fallback` and stating that it carries no demonstrated edge.

## Metrics

Primary metric: **log loss**. Companions: Brier, ranked probability score, expected calibration
error, calibration slope, top-1/3/5 accuracy. Uniform reference floors: log loss `2.302585`,
Brier `0.9`, accuracy `0.1`.

Seven baselines: uniform, expanding frequency, rolling frequency (w=50), Bayesian (Laplace and
Jeffreys), recency-weighted, first-order Markov.

## CLI

```
python -m src.cli.main [--dataset live|synthetic_null|synthetic_signal] <command>

  init          [--market ...] [--rebuild]      create/migrate each market's database
  synthetic     [--rebuild]                     regenerate the control world
  discover                                      probe the configured sources
  extract       [--market ...] / extract-all    crawl historical charts
  validate      [--market ...]                  data-quality gate
  analyse       [--market ...] [--target ...]    run the 100-method suite
  cross-market  [--market A B]                  dependency, lead-lag, conditional models
  backtest      --market M [--target ...]       walk-forward with baselines
  predict       --market M --target open|close  next-draw distribution
  ledger        --market M [--target ...]       score stored forecasts
  update-all    [--market ...]                  update → validate → analyse → forecast
  methods       [--category A..H] [--write]     catalogue and dossiers
  report                                        build the Section 22 report
  status                                        database state
```

**Market isolation is a hard rule in the interface**: every analysis command takes a single
`--market`. Multi-market output exists only in `cross-market` (inherently comparative) and in
`predict --compare A B`, which must be requested explicitly.

## What is honest here, and what is not

**Executed and verified in this repository:**

- 100/100 methods documented, implemented and executed against all markets and targets;
- `validate_registry()` → `ok: True`, 100 documented, 100 implemented, zero problems;
- per-market schema v3 with all required tables, integrity `ok`, provenance and revision logs;
- 73-column causal feature matrix with `verify_causality` passing (0 leaked columns);
- walk-forward backtests for 10 estimators × 7 baselines on both targets;
- cross-market lead-lag sweep (28 tests per pair), dependency battery, leakage validation, and
  the decisive conditional-model comparison;
- forecasts and a scoring ledger;
- ~70 tests covering parsing, storage, quality gates, mathematics, backtesting, cross-market
  alignment and predictions — no network required.

**Not executed, and not claimed:**

- **No live extraction.** Zero real records were retrieved; the extraction code path is exercised
  only against HTML fixtures.
- **No live incremental update** has ever run against a source.
- **No model was promoted**, so no forecast in this repository has demonstrated predictive value.

See [`docs/RESULTS_synthetic_null.md`](docs/RESULTS_synthetic_null.md) and
[`docs/RESULTS_synthetic_signal.md`](docs/RESULTS_synthetic_signal.md) for machine-generated
tables read directly from the databases, [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md) for the
extraction blockers, and `research/reports/SECTION_22_REPORT_*.md` for the full A–G report.

## Data and secrets policy

- Databases, WAL files, raw HTML, Parquet extracts and model pickles are git-ignored; only
  fixtures and `MANIFEST.json` digests are committed. **No binary database is committed.**
- No credentials are stored in the repository. `.env.example` documents the variables that
  exist; none are required for the synthetic pipeline.
- Scraping, when it is eventually run against a live source, is rate-limited, robots-aware and
  never bypasses authentication, CAPTCHAs or paywalls.
